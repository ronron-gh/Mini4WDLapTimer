# 更新・レビュー規則

## 章への配置

| 追加・変更の内容 | 更新する章 |
| --- | --- |
| 新しい周辺機器・依存・ビルド構成 | 2、4、必要に応じ6〜12 |
| 新機能・既存機能の動作変更 | 3、6と影響する章 |
| 状態・入力優先度・キャンセル | 5、6、8、9、10、12 |
| タスク・ISR・優先度・処理順 | 7、4、8、11、12 |
| 共有バッファ・通知・ACK・保存 | 8、5、6、10〜12 |
| 画面・ボタン・ログ・プロトコル | 9、5、6、11、12 |
| エラー検出・復旧・タイムアウト | 10、5〜8、11、12 |
| 測定分解能・応答・RAM等の制約 | 11、関連する機能、12 |
| 未確定値・実測待ち・差異 | 12。決定後は本来の節へ移す。 |
| 実装経緯・レビュー・不具合の履歴 | 作業記録。現行設計への影響だけ本来の章へ。 |

機能IDを再採番せず、見出しの移動時は内部参照を更新する。機能一覧を更新したら検証表も対応させる。削除する機能は参照・操作・状態・テストの残りを確認する。

## 再構成時の照合

旧章の内容を「現行」「置換済み」「履歴」「未確定」に仕分ける。現行の制約・公開契約・異常・境界値を落とさず意味の章へ移す。置換済みの値を最新値と混ぜない。根拠が足りない項目は保留として残す。

実装予定と現行コードが違う場合、どちらが合意済みかを確認する。文書だけで実装を正当化したり、未承認の変更を確定にしない。

## 完了確認

- 同じ値・操作・状態について矛盾する説明がない。
- 機能の入力、出力、副作用、事前条件、復旧方法が追える。
- 通知を落としてよいか、配列をいつ書き換えてよいかが明確。
- 共通構成と構成固有の責務が区別され、時刻・単位が一貫する。
- 画像、相対リンク、要求参照、検証参照が有効。
- 実機未確認・未測定が実測済みとして書かれていない。
- 実装段階名のトップレベル章を追加していない。
